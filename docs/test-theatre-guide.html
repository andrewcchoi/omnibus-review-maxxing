Test Theatre Detection Guide

Identify tests that pass but provide no real protection

← Back to README

What is Test Theatre?

Theatre tests are worse than no tests. They create false confidence that your code is protected while providing zero actual verification. Features fail in production despite "passing tests."

Test theatre refers to tests that appear to validate functionality but actually verify nothing meaningful. They inflate coverage metrics, pass CI checks, and give developers a false sense of security.

The False Confidence Problem

80%
Reported Coverage
45%
Real Coverage
0
Bugs Caught

When theatre tests are counted as coverage, metrics become meaningless. A team might believe they have 80% coverage while actually having 45% real protection. Bugs slip through the "safety net" because the net has invisible holes.

The dependency exists because:

  • Coverage analyzer maps tests to production code
  • If a theatre test exists for a function, coverage analyzer marks it as "covered"
  • But theatre tests provide NO actual coverage

Correct workflow:

  1. Theatre detector identifies fake tests and outputs a list
  2. Coverage analyzer receives the list and excludes those tests from metrics
  3. Coverage metrics now reflect reality

Theatre Test Patterns

1 Hardcoded Input/Output

Tests where both input and expected output are literals with trivial relationship.

Theatre
# What if add() always returns 5?
def test_add():
    assert add(2, 3) == 5
Real Test
# Tests actual behavior
def test_add():
    assert add(0, 0) == 0
    assert add(-1, 1) == 0
    assert add(100, 200) == 300

Detection Criteria

  • Single assertion with literal input and literal output
  • No variation in inputs tested
  • No edge cases (zero, negative, boundary values)
  • Relationship between input and output is trivial

2 Empty Test Body

Tests that are placeholders, never implemented.

Theatre
def test_payment_processing():
    pass

def test_user_validation():
    ...

def test_order_flow():
    """TODO: implement"""

Detection Criteria

  • Test body is pass, ..., or only docstring/comments
  • No actual code execution
  • No assertions

3 Always-Pass Assertions

Assertions that can never fail regardless of code behavior.

Theatre
def test_something():
    result = process_data()
    assert True
    assert 1 == 1
    assert "test" == "test"
    assert result or True  # Short-circuit always passes

def test_config():
    assert 5 > 3  # Tests nothing about your code

Detection Criteria

  • assert True
  • assert <literal> == <literal>
  • assert <expr> or True
  • Assertions with no connection to code under test

4 Over-Mocked Tests

Everything is mocked, so the test verifies mock configuration, not real behavior.

Theatre
@patch('module.database')
@patch('module.cache')
@patch('module.api_client')
@patch('module.validator')
def test_process(mock_val, mock_api,
                 mock_cache, mock_db):
    mock_db.get.return_value = {"id": 1}
    mock_api.fetch.return_value = {"data": "x"}

    result = process_item(1)

    # Just testing mock config!
    assert result == {"id": 1, "data": "x"}
Real Test
# Integration test - real database
def test_process(test_db):
    test_db.insert({"id": 1, "value": 100})

    result = process_item(1)

    # Tests actual transformation
    assert result["computed"] == 200
    assert result["processed_at"] is not None

Detection Criteria

  • 3+ mocks/patches in single test
  • Return values configured for all mocks
  • Assertion verifies the exact mock return values
  • No real code path exercised

5 Mock-Only Assertions

Tests that only verify mocks were called, not that results are correct.

Theatre
def test_send_email():
    with patch('mailer.send') as mock:
        notify_user(user_id=1)
        # Called, but correct content?
        mock.assert_called_once()
Real Test
def test_send_email():
    with patch('mailer.send') as mock:
        notify_user(user_id=1)
        mock.assert_called_once_with(
            to="user@example.com",
            subject="Welcome",
            body=contains("Hello John")
        )

Detection Criteria

  • Only assert_called() or assert_called_once() without arguments
  • No verification of call arguments
  • No verification of side effects or return values

6 Tautological Tests

Tests that verify the test setup, not the code behavior.

Theatre
# Testing that mock returns what you set
def test_get_user():
    mock_repo = Mock()
    mock_repo.get.return_value = User(id=1, name="Test")

    service = UserService(mock_repo)
    user = service.get_user(1)

    assert user.name == "Test"  # You set this!

# Testing fixture data
def test_user_fixture(user_fixture):
    assert user_fixture.email == "test@test.com"

Detection Criteria

  • Assertion verifies exact value that was configured in mock
  • No transformation or business logic between mock and assertion
  • Testing fixture data instead of code behavior

7 Exception Swallowing

Tests that catch and ignore exceptions, so they pass even when code fails.

Theatre
# Swallows real failures
def test_dangerous_operation():
    try:
        result = dangerous_operation()
        assert result is not None
    except Exception:
        pass  # Test passes even on failure!

# Masks the failure
def test_api_call():
    try:
        response = api.call()
    except:
        response = None
    # Always passes!
    assert response is None or response.ok

Detection Criteria

  • except block with pass or empty body
  • except Exception or bare except that doesn't re-raise
  • Assertion after except that allows None/failure case

8 Conditional Assertions

Assertions inside conditionals that may never execute.

Theatre
# Assertion might never run
def test_feature_flag():
    result = process()
    if result.success:
        assert result.data is not None
    # What if success is always False?

# Environment-dependent
def test_integration():
    if os.getenv('RUN_INTEGRATION'):
        result = integration_call()
        assert result.ok
    # Passes with no assertions in CI!

Detection Criteria

  • assert inside if block
  • No else clause with assertion or failure
  • Condition may commonly be False

9 Trivial Assertions

Assertions that almost never fail in practice.

Theatre
def test_returns_something():
    result = fetch_data()
    # Almost always true
    assert result is not None
    assert isinstance(result, dict)
    assert len(result) > 0

def test_user_has_fields():
    user = get_user(1)
    # Field exists, but valid?
    assert hasattr(user, 'email')
Real Test
def test_fetch_user_data():
    result = fetch_data(user_id=1)
    assert result["user_id"] == 1
    assert result["email"] == "test@example.com"
    assert result["created_at"] < datetime.now()

def test_user_email_valid():
    user = get_user(1)
    assert "@" in user.email
    assert user.email.endswith(".com")

Detection Criteria

  • is not None as only assertion
  • isinstance() checks without value verification
  • hasattr() or in checks without value assertions
  • len() > 0 without content verification

10 Snapshot Theatre

Snapshot tests that just verify "code hasn't changed" without verifying correctness.

Theatre
# If original was wrong, this passes forever
def test_render_component(snapshot):
    result = render_component(data)
    assert result == snapshot

# 10,000 line snapshot nobody reads
def test_api_response(snapshot):
    response = api.get('/users')
    snapshot.assert_match(response.json())

Detection Criteria

  • Snapshot tests for complex objects (>100 lines)
  • Snapshot tests without clear expected behavior
  • Snapshots that were created without review

Severity Classification

Theatre test severity depends on what the test claims to cover:

CRITICAL

Theatre test claims to cover critical functionality:

  • Payment processing
  • Authentication/authorization
  • Data integrity operations
  • Security controls

Impact: Critical bugs reach production with "passing tests"

HIGH

Theatre test covers important features:

  • Core business logic
  • User-facing workflows
  • API endpoints
  • Data transformations

Impact: Major functionality may fail despite passing tests

MEDIUM

Theatre test covers secondary functionality:

  • Edge case handling
  • Error messages
  • Logging/monitoring
  • Configuration handling

Impact: Non-critical issues may go undetected

Theatre vs. Legitimate Patterns

Not all simple tests are theatre. Here's how to distinguish:

Pattern Theatre Legitimate
Single assertion assert add(2,3) == 5 (only case) assert add(2,3) == 5 (one of many cases)
Not None check Only assertion in test Guard before value assertions
Mock usage 4+ mocks, testing mock config 1-2 mocks for isolation, testing real logic
Exception handling except: pass with pytest.raises(ValueError):
Snapshot test Large, never-reviewed snapshots Small, intentional golden files

      "id": "theatre-001",

The coverage analyzer uses this output to:

  • Exclude theatre tests from coverage calculations
  • Report accurate "effective coverage" metrics
  • Flag functions that appear covered but aren't

Fixing Theatre Tests

A theatre test should either be fixed or deleted. A deleted test is honest. A theatre test is a lie.

Fix Strategies by Pattern

Pattern Fix Strategy
Empty body Implement the test or delete it
Hardcoded I/O Add multiple cases, edge cases, parameterization
Always-pass Replace with meaningful assertions on actual behavior
Over-mocked Reduce mocks, test real integration, or write integration tests
Mock-only Assert on call arguments and/or return values
Tautological Assert on transformations, not passthrough values
Exception swallow Use pytest.raises() for expected exceptions
Conditional Remove condition or add else with pytest.fail()
Trivial Add specific value assertions
Snapshot theatre Break into specific assertions or review/approve snapshots
