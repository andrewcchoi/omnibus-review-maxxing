Complete Workflow Overview

Phase 1: Pre-Review Validation

Step 1: Git Status Check

  • Verify repository is a valid git repo
  • Check for staged changes with git diff --cached
  • Identify modified files and line ranges
  • Exit with error if no staged changes found

Step 2: Documentation Gathering

  • Read CLAUDE.md for project patterns and conventions
  • Read README.md for architecture overview
  • Parse package.json/pyproject.toml for dependencies
  • Identify technology stack (languages, frameworks)

Step 3: Project Structure Analysis

  • Map directory structure and module organization
  • Identify test directories and patterns
  • Locate configuration files
  • Build dependency graph for changed files

Step 4: Context Package Creation

  • Compile relevant context for each agent
  • Include staged diff with full context
  • Add related unchanged files for reference
  • Package project conventions and patterns

Phase 2: Parallel Specialist Review

Agent Independence

Each agent operates in isolation with:

  • No knowledge of other agents' findings
  • Independent reasoning and judgment
  • Domain-specific focus areas
  • Same context package but different analytical lens

Why? Prevents groupthink, maximizes coverage, allows specialization

Execution Time

  • Sequential estimate: 6 agents × 2 min avg = 12 minutes
  • Parallel actual: ~2-3 minutes (longest agent determines total)
  • Trade-off: Higher API cost for 6× faster results

Phase 3: Aggregation & Prioritization

Phase 4: Parallel Fix Cycle

Entry Conditions

Phase 4 is triggered when user specifies --fix flag.

Key principle: No confirmation prompts. All fixes proceed automatically with complete solutions.

Step 1: Planning

  • Group findings by file
  • Generate YAML fix plan per file
  • Include architecture context from CLAUDE.md
  • Define planned fix for each finding

Step 2: Parallel Fixers

Spawn one omnibus-fixer subagent per file (in parallel):

  • Each fixer receives ONLY its file + fix plan (minimal context)
  • Apply COMPLETE fixes - no shortcuts
  • Fixes must fit existing architecture
  • Update plan with status and actual_fix
  • Document divergence reasons if deviating from plan

Step 3: Parallel Validators

Spawn one omnibus-validator subagent per fixed file (in parallel):

  • Read updated fix plan + git diff
  • Verify each fix was actually applied
  • Check fixes are COMPLETE (not shortcuts)
  • Validate architecture alignment
  • Assess divergence reasons
  • Flag regressions or new issues

Step 4: Re-Review

  • Run 6 review agents on modified files only
  • Aggregate new findings
  • If CRITICAL/HIGH remain: loop back to Planning
  • If max iterations reached: exit with summary

Success Path

  • All CRITICAL/HIGH issues resolved
  • All fixes validated as complete
  • Changes ready to commit
  • Fix plans archived for audit trail

Failure Scenarios

  • Max iterations: Some issues remain unfixed after limit reached
  • Validation failure: Fixer applied incomplete fix, flagged by validator
  • Regression: Fix introduced new issues, caught by re-review
  • Cross-file dependency: Fix requires changes to multiple files

Result: Report remaining issues for manual resolution

Context Isolation Benefit

Each subagent starts with fresh context:

  • Fixers receive only: file + plan + architecture context
  • Validators receive only: file + plan + git diff
  • No compaction needed during fix loop
  • Scales to any number of files

Timing Estimates

Phase Estimated Time Notes
Phase 1: Pre-Review 15-30 seconds Reading local files, fast
Phase 2: Agent Review 2-4 minutes Parallel, ultrathink adds time
Phase 3: Aggregation 10-20 seconds Local processing
Phase 4: Fix Cycle 5-15 minutes Varies by issue count, test time
Total (without fix) 3-5 minutes Report-only mode
Total (with fix) 8-20 minutes Includes automated fixes
