Severity Classification Guide

How Omnibus Review assigns and interprets issue severity levels

← Back to README

Severity Levels Overview

Omnibus Review classifies all findings into four severity levels based on impact, exploitability, and urgency. Each level has specific characteristics and recommended actions.

CRITICAL Immediate Action Required

Timeline: Fix immediately, do not merge

Typical Issues:

  • Remote code execution vulnerabilities
  • SQL injection, command injection
  • Authentication bypass
  • Hardcoded credentials in production code
  • Data loss scenarios (destructive operations without safeguards)
  • Production-breaking bugs in critical paths

Auto-fix: Attempted automatically with --fix flag

HIGH Fix Before Merge

Timeline: Must fix before merging to main/production

Typical Issues:

  • Cross-site scripting (XSS)
  • Insecure deserialization
  • Missing authorization checks
  • Logic errors causing incorrect behavior
  • N+1 query problems affecting performance
  • Resource exhaustion vulnerabilities
  • Unhandled exceptions in main flows

Auto-fix: Attempted automatically with --fix flag

MEDIUM Fix Soon

Timeline: Fix within current sprint or before next release

Typical Issues:

  • Missing input validation (low-risk endpoints)
  • Inefficient algorithms in non-critical paths
  • Test coverage gaps
  • Code duplication
  • Missing error handling in edge cases
  • Suboptimal database queries
  • Architectural violations (minor)

Auto-fix: Not attempted by default

LOW Consider Fixing

Timeline: Fix when convenient, consider technical debt backlog

Typical Issues:

  • Style inconsistencies
  • Missing documentation
  • TODO comments
  • Overly complex but working code
  • Minor performance optimizations
  • Unused imports or variables
  • Suggestions for future improvements

Auto-fix: Not attempted

Impact Definitions

  • Critical Impact: System compromise, data breach, financial loss, or complete service outage
  • High Impact: Feature malfunction, data corruption, significant performance degradation
  • Medium Impact: Minor functionality issues, user experience problems, maintainability concerns
  • Low Impact: Cosmetic issues, code quality concerns, documentation gaps

Exploitability Definitions

  • High: Trivial to exploit, affects common paths, no authentication required
  • Medium: Requires specific conditions, authenticated access, or unusual input
  • Low: Complex exploitation, requires privileged access, or very rare conditions

Detailed Examples by Category

Security Issues

CRITICAL SQL Injection
query = f"SELECT * FROM users WHERE id = {user_id}"

Why Critical: Direct database access, trivial to exploit, high impact

Fix: Use parameterized queries

HIGH XSS Vulnerability
return f"<div>Hello {username}</div>"

Why High: User impact, easy to exploit, but limited scope

Fix: HTML escape user input

MEDIUM Weak Password Policy
min_password_length = 6

Why Medium: Security concern but requires user cooperation to exploit

Fix: Increase minimum to 12+ characters

LOW Missing Security Headers
// No X-Frame-Options header

Why Low: Defense-in-depth measure, low immediate risk

Fix: Add security headers middleware

Correctness Issues

CRITICAL Data Loss
await session.delete(user) # No safeguards or confirmation

Why Critical: Irreversible data destruction

Fix: Add soft-delete or confirmation mechanism

HIGH Off-by-One Error
for i in range(len(items)): # Missing last item

Why High: Logic error causing incorrect results

Fix: Use correct range or iterate directly

MEDIUM Unhandled Exception
result = json.loads(response.text) # May raise ValueError

Why Medium: Edge case that crashes feature

Fix: Add try/except with appropriate handling

LOW Unused Variable
temp = calculate_value() # Never used

Why Low: Code smell, no functional impact

Fix: Remove unused code

Performance Issues

HIGH N+1 Query
for user in users: print(user.profile.name) # Query per user

Why High: Causes timeout/crash with many users

Fix: Use eager loading or join

MEDIUM Missing Index
SELECT * FROM logs WHERE user_id = ? # No index on user_id

Why Medium: Slow queries but not breaking

Fix: Add database index

LOW Inefficient Sort
items.sort(key=lambda x: expensive_fn(x)) # Called repeatedly

Why Low: Micro-optimization, minor impact

Fix: Cache expensive_fn results

Architecture Issues

HIGH Circular Dependency
from module_a import X # module_a also imports from this file

Why High: Breaks modularity, hard to test/maintain

Fix: Refactor to remove circular reference

MEDIUM God Object
class Manager: # 50+ methods, 2000+ lines

Why Medium: Maintainability issue, not immediate bug

Fix: Split into focused classes

LOW Missing Abstraction
if user.role == "admin": ... # Repeated across codebase

Why Low: Code quality issue, suggests refactor

Fix: Create has_permission() method

Confidence Thresholds

Each finding includes a confidence score (0.0-1.0) representing how certain the agent is that the issue is real and not a false positive.

0.9 - 1.0 Very High Confidence

Clear violation, well-established pattern, agent has high certainty

0.8 - 0.9 High Confidence

Strong evidence, minor possibility of false positive

0.7 - 0.8 Moderate Confidence (Default Threshold)

Likely issue, requires human review to confirm

0.6 - 0.7 Low Confidence

Possible issue, higher false positive rate - filtered by default

< 0.6 Very Low Confidence

Speculative finding, likely false positive - filtered by default

Adjusting Confidence Threshold

Use the --confidence flag to adjust filtering:

  • --confidence 0.9 - Highest quality, fewest findings
  • --confidence 0.7 - Default balanced setting
  • --confidence 0.5 - Aggressive, more false positives

Severity Upgrading Rules

The aggregator may upgrade severity when multiple agents independently identify the same issue or related issues that compound impact.

Multi-Agent Agreement

  • 2 agents agree: +1 confidence, consider severity upgrade
  • 3+ agents agree: +0.15 confidence, upgrade severity one level if near boundary
  • Security + Correctness agree: Strong signal, prioritize highly

Compound Issues

Related issues that together create higher risk:

  • Missing validation + database query = potential injection (upgrade to HIGH/CRITICAL)
  • Multiple auth bypass paths = systemic issue (upgrade severity)
  • Performance issue in hot path = user-facing impact (upgrade to HIGH)

Context-Based Adjustments

  • Production code: Upgrade severity for user-facing issues
  • Test code: Downgrade severity (less critical than production)
  • Public API: Upgrade security findings (larger attack surface)
  • Internal tools: Downgrade if not exposed externally

Reporting Thresholds

Control which severities appear in final report:

Flag Reports Use Case
--min-severity critical CRITICAL only Emergency audits, hotfix validation
--min-severity high CRITICAL + HIGH Pre-merge quick check
--min-severity medium CRITICAL + HIGH + MEDIUM Sprint planning, technical debt
--min-severity low (default) All findings Comprehensive review
