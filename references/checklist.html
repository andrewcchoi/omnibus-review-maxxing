Review Checklist

Comprehensive preparation and post-review actions for Omnibus Review

Pre-Review Preparation

Complete these steps before running /omnibus-review to ensure the best results.

Essential Prerequisites (Required)

  • Stage changes you want reviewed with git add
  • Ensure working directory has no uncommitted changes that would interfere
  • Verify you're on the correct branch
  • Confirm tests are passing locally
# Check current status git status # Stage specific files git add path/to/modified/file.py # Or stage all changes git add . # Verify what's staged git diff --cached --stat

Code Quality Checks (Recommended)

  • Run linters (ruff, eslint, etc.) and fix auto-fixable issues
  • Run formatters (black, prettier, etc.) for consistent style
  • Run type checkers (mypy, TypeScript compiler) and fix errors
  • Ensure all tests pass with pytest or equivalent
  • Remove debug code, console.logs, and commented-out code
Pro Tip: Run local quality checks first to avoid having omnibus-review flag issues that automated tools could have caught instantly. This saves review time and keeps findings focused on deeper issues.

Documentation Updates (Recommended)

  • Update CLAUDE.md if you're introducing new patterns or conventions
  • Update README.md if you're changing setup instructions or architecture
  • Add/update docstrings for new public functions and classes
  • Update API documentation if you changed endpoint signatures
  • Add comments for complex logic or non-obvious decisions

Test Coverage (Recommended)

  • Write tests for new features before review
  • Add edge case tests for critical paths
  • Update existing tests if you changed behavior
  • Verify test names are descriptive and follow project conventions
  • Check that test coverage hasn't decreased
# Python test coverage pytest --cov=src tests/ coverage html # Generate HTML report # JavaScript/TypeScript test coverage npm test -- --coverage

Running the Review

Phase 1: Initial Review (Report Only)

Start with a report-only review to understand the scope of issues:

/omnibus-review

Duration: 3-5 minutes typically

Output: Full report of all findings without making changes

Phase 2: Quick Triage (High-Priority Only)

If time is limited, focus on critical and high severity issues first:

/omnibus-review --min-severity high

Duration: 2-3 minutes typically

Output: Only CRITICAL and HIGH findings

Phase 3: Automated Fixes (Optional)

After reviewing findings, apply automated fixes:

/omnibus-review --fix

Duration: 8-20 minutes typically (includes re-testing)

Output: Fixed code with staged changes

Important: Always review the automated fixes before committing. While the fix cycle includes testing, it's still important to understand what changed.

Post-Review Actions

Review Findings (Critical Priority)

  • Read all CRITICAL findings and fix immediately
  • DO NOT MERGE if any CRITICAL issues remain
  • Verify security vulnerabilities are fully resolved
  • Rotate any exposed credentials (API keys, passwords)

Address High-Priority Issues

  • Fix all HIGH severity issues before merging to main/production
  • Review automated fixes if --fix was used
  • Test fixed code manually in addition to automated tests
  • Consider if HIGH issues indicate broader architectural problems

Triage Medium/Low Issues

  • Create tickets for MEDIUM issues in project tracker
  • Assign to appropriate sprint or backlog
  • Group related issues for batch fixing
  • Consider addressing LOW issues during refactoring

Review Staged Changes

  • Review all staged changes with git diff --cached
  • Verify automated fixes are correct and don't break functionality
  • Check that no unintended changes were made
  • Run full test suite one more time
# Review what will be committed git diff --cached # Review specific file git diff --cached path/to/file.py # Interactive staging review git add -p

Commit Changes

  • Write clear commit message describing fixes
  • Reference issue numbers if applicable
  • Consider splitting unrelated fixes into separate commits
  • Include link to omnibus-review report if saved
# Good commit message examples git commit -m "fix: Address critical security findings from omnibus-review - Fix SQL injection in payment processing (C-1) - Remove hardcoded API keys, use env vars (C-2) - Resolve N+1 query in subscription loader (H-1) See: .omnibus-review/report_2026-05-23_143215.json" # Or use interactive commit for fine control git commit -v

Common Issue Patterns

Recurring patterns to watch for and address proactively:

Security Patterns

  • SQL injection from string interpolation → Use parameterized queries
  • XSS from unescaped user input → Use template auto-escaping or explicit escape
  • Hardcoded credentials → Move to environment variables
  • Missing authentication checks → Add auth middleware
  • Insecure random numbers → Use secrets module for crypto
  • Path traversal risks → Validate and sanitize file paths

Correctness Patterns

  • Off-by-one errors in loops → Use correct range boundaries
  • Null/undefined dereferencing → Add null checks or optional chaining
  • Race conditions → Add proper locking or use atomic operations
  • Unhandled exceptions → Add try/catch with appropriate recovery
  • Type coercion bugs → Use strict equality and explicit conversions
  • Integer overflow → Validate numeric bounds

Performance Patterns

  • N+1 queries → Use eager loading or joins
  • Missing indexes → Add indexes on frequently queried columns
  • Inefficient loops → Consider list comprehensions or bulk operations
  • Memory leaks → Ensure cleanup in finally blocks or context managers
  • Blocking I/O in async → Use async/await consistently
  • No caching → Add caching for expensive computations

Architecture Patterns

  • Circular dependencies → Extract shared logic to common module
  • God objects → Split into focused, single-purpose classes
  • Missing abstractions → Create interfaces or base classes
  • Tight coupling → Use dependency injection
  • Duplicate code → Extract to shared utilities
  • Inconsistent patterns → Follow established project conventions

When to Re-Run Review

Consider running omnibus-review again in these scenarios:

  • After fixing CRITICAL/HIGH issues to verify resolution
  • After significant refactoring to catch regressions
  • Before final merge to main/production branch
  • After merging upstream changes that conflict with your fixes
  • If you added substantial new code during fix phase
  • When confidence threshold flags seem too aggressive (adjust with --confidence)
Verification Run: After fixing issues, run with high confidence to verify:
/omnibus-review --min-severity high --confidence 0.85
This ensures no new critical issues were introduced and original issues are truly resolved.

Integration with CI/CD

Best practices for incorporating omnibus-review into automated pipelines:

Pre-Merge Gate

  • Run omnibus-review on pull requests automatically
  • Block merge if CRITICAL issues found
  • Require approval for HIGH issues
  • Generate report as PR comment

Scheduled Audits

  • Run weekly full-codebase review on main branch
  • Track issue trends over time
  • Generate security reports for compliance
  • Alert on new CRITICAL findings
CI Configuration Example: Parse JSON output for automated decision-making:
# In CI script /omnibus-review --min-severity high --output report.json critical_count=$(jq '.summary.by_severity.critical' report.json) if [ "$critical_count" -gt 0 ]; then echo "CRITICAL issues found - blocking merge" exit 1 fi

Troubleshooting Checklist

Review Won't Start

  • Verify git repository is initialized
  • Check that changes are staged with git add
  • Ensure you're not in detached HEAD state
  • Verify Claude Code plugin is enabled

Too Many False Positives

  • Increase confidence threshold: --confidence 0.85
  • Update CLAUDE.md with project-specific patterns
  • Filter to higher severities: --min-severity medium
  • Check if agents have sufficient context (large refactor may confuse)

Review Taking Too Long

  • Limit to specific files: --files "src/critical/**"
  • Run quick triage first: --min-severity high
  • Split large changes into smaller reviewable chunks
  • Check for timeout issues with very large files

Fixes Not Working

  • Ensure tests pass before running --fix
  • Check for missing environment variables
  • Review rollback messages for specific failure reasons
  • Some issues require manual judgment (expected behavior)

Quick Reference Commands

Common Workflows

# Standard comprehensive review /omnibus-review # Quick pre-merge check (critical + high only) /omnibus-review --min-severity high # Full review with auto-fix /omnibus-review --fix # Focus on security changes only /omnibus-review --files "src/auth/**/*.py" --min-severity high # High-confidence findings only (reduce false positives) /omnibus-review --confidence 0.9 # Review specific area with fix /omnibus-review --files "src/payment/**" --fix --max-iterations 3

Git Commands for Review Workflow

# Prepare for review git add -p # Interactively stage changes git diff --cached # Review what's staged # After review git diff --cached # Review automated fixes git commit -v # Commit with verbose diff # If you need to unstage git reset HEAD path/to/file # Unstage specific file git reset # Unstage all # Create review checkpoint git stash # Save work-in-progress /omnibus-review # Run review on clean state git stash pop # Restore work
